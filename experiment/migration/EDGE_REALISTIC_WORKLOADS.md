# 边缘计算真实负载场景设计指南

## 一、边缘缓存的意义和使用场景

### 1.1 边缘缓存的核心价值

边缘缓存在边缘计算中扮演关键角色，主要解决以下问题：

1. **降低延迟**: 将数据和计算移近数据源，减少云端往返时间（RTT）
   - 工业场景：传感器数据 → 边缘缓存 → 本地决策（<10ms）
   - 云端场景：传感器数据 → 云端处理 → 回传（50-200ms）

2. **减少带宽成本**: 边缘过滤、聚合数据后再上传
   - 例：摄像头产生 10MB/s，边缘处理后仅上传事件数据（10KB/s）
   - 带宽节省比：~99.9%

3. **离线可用性**: 网络断连时边缘节点继续运行
   - 关键任务场景（矿井、海上平台）必须保证离线可用

4. **数据合规性**: 敏感数据本地处理，避免传输到云端
   - 医疗：患者隐私数据本地分析
   - 工业：生产工艺参数不出厂

### 1.2 真实边缘场景分类

#### **实时分析缓存** (Real-time Analytics Cache)
- **场景**: 边缘流处理、实时监控、异常检测
- **特点**:
  - 高写入吞吐（10K-100K writes/sec）
  - 时间窗口查询（最近N秒/分钟）
  - 内存优先，定期持久化
- **典型应用**:
  - 智能制造：设备振动监测、产线质量实时统计
  - 智慧城市：交通流量实时统计、环境监测

#### **推理结果缓存** (Inference Result Cache)
- **场景**: AI模型推理结果临时存储
- **特点**:
  - 读写混合（70%读/30%写）
  - TTL管理（结果有时效性）
  - 缓存命中率优化
- **典型应用**:
  - 视频分析：人脸/车牌识别结果缓存
  - 工业视觉：缺陷检测结果缓存

#### **状态同步缓存** (State Synchronization Cache)
- **场景**: 多边缘节点间状态共享
- **特点**:
  - 强一致性需求
  - 发布订阅模式
  - 心跳/健康检查
- **典型应用**:
  - 协同机器人：位置、任务状态共享
  - 车联网：V2V/V2I通信

#### **会话状态存储** (Session State Store)
- **场景**: 用户会话、设备会话管理
- **特点**:
  - 内存优先（热数据）
  - 持久化备份（冷数据）
  - 高可用性要求
- **典型应用**:
  - 零售：顾客购物会话、推荐缓存
  - 游戏：边缘游戏服务器状态

## 二、真实边缘应用场景与容器实现

### 2.1 工业物联网 (Industrial IoT)

#### **场景1: 预测性维护 (Predictive Maintenance)**

**业界应用实例**:
- **GE Digital Predix**: 工业设备监控与预测维护
- **西门子 MindSphere**: 设备健康监测
- **施耐德电气 EcoStruxure**: 能源管理与设备监控

**内存优先原因**:
- 实时振动/温度数据流分析（每秒数千个数据点）
- 滑动窗口特征计算（最近5分钟统计量）
- 异常检测需要亚秒级响应

**容器化方案**:
```yaml
容器类型: InfluxDB + Redis
- InfluxDB: 存储时序传感器数据（分钟级聚合持久化）
- Redis Streams: 实时数据流缓冲（秒级数据）
- Redis Sorted Sets: 最近N条数据的快速查询

数据流:
传感器 → Redis Stream → 流处理 → 异常检测 →
  ├─→ 正常: 丢弃或批量聚合到InfluxDB
  └─→ 异常: 触发告警 + 详细数据持久化
```

**基准负载设计**:
```python
# 文件: experiment/migration/industrial/bench_predictive_maintenance.py
特点:
- 多传感器类型: 振动(加速度xyz)、温度、压力、电流
- 真实物理约束: 传感器漂移、采样率变化、数据突变
- 异常模拟: 周期性故障模式注入（轴承磨损、温度异常）
- 混合负载: 90%写入（数据采集）+ 10%读取（窗口查询）
```

#### **场景2: 工业视觉质检 (Automated Visual Inspection)**

**业界应用实例**:
- **Cognex In-Sight**: 视觉检测系统
- **Keyence CV-X**: 图像处理与缺陷检测
- **Landing AI**: 制造业AI视觉平台

**内存优先原因**:
- 高速产线：100-300件/分钟，推理结果需即时缓存
- 上下文关联：当前缺陷与前N个检测结果比对
- 统计分析：实时合格率、缺陷趋势

**容器化方案**:
```yaml
容器类型: Redis + Elasticsearch
- Redis Hashes: 最近1000个检测结果（滚动窗口）
- Redis HyperLogLog: 实时统计合格率
- Elasticsearch: 缺陷数据持久化与历史分析

数据流:
产线相机 → AI推理 → Redis写入 →
  ├─→ 缓存未命中: 新检测
  └─→ 缓存命中: 相同产品重复检测（跳过）
定期批量: Redis → Elasticsearch（每分钟）
```

### 2.2 智能零售 (Smart Retail)

#### **场景3: 实时推荐引擎 (Real-time Recommendation)**

**业界应用实例**:
- **Amazon Go**: 无人零售店实时商品识别与推荐
- **阿里云IoT边缘计算**: 智慧门店解决方案
- **京东智联云边缘计算**: 零售场景边缘推理

**内存优先原因**:
- 顾客行为实时跟踪（停留时长、浏览商品）
- 推荐结果需<100ms响应
- 购物车状态频繁更新

**容器化方案**:
```yaml
容器类型: Redis + PostgreSQL (边缘轻量版)
- Redis Hashes: 用户会话状态、购物车
- Redis Sorted Sets: 热门商品排行（实时更新）
- Redis Pub/Sub: 优惠券推送、促销通知
- PostgreSQL: 订单持久化、库存管理

数据流:
顾客进店 → 创建会话 (Redis) →
  商品浏览 → 更新会话状态 → 触发推荐计算 →
  加入购物车 → Redis更新 →
  结账 → 同步到PostgreSQL
```

**基准负载设计**:
```python
# 文件: experiment/migration/retail/bench_realtime_recommendation.py
特点:
- 会话生命周期: 创建 → 浏览 → 购物车操作 → 结账/放弃
- 真实行为模拟: 停留时间分布、购物车弃单率、复购行为
- 混合操作: 50%读取(商品查询) + 40%写入(行为记录) + 10%更新(购物车)
- 峰值模拟: 促销时段流量突增（2-5倍）
```

### 2.3 智慧交通 (Intelligent Transportation)

#### **场景4: V2X通信与协同感知 (V2X Communication)**

**业界应用实例**:
- **华为C-V2X**: 车路协同平台
- **百度Apollo**: 自动驾驶边缘计算
- **移动5G MEC**: 车联网低延迟通信

**内存优先原因**:
- 超低延迟要求（<10ms）
- 车辆位置实时更新（10Hz-100Hz）
- 交通事件即时广播

**容器化方案**:
```yaml
容器类型: Redis (主) + TimescaleDB (辅)
- Redis Geo: 车辆实时位置索引（GEOADD/GEORADIUS）
- Redis Pub/Sub: 交通事件广播（事故、拥堵）
- Redis Streams: 车辆轨迹流
- TimescaleDB: 历史轨迹持久化

数据流:
车辆OBU → 位置更新 (Redis Geo) →
  查询周边车辆 (GEORADIUS 500m) →
  碰撞风险计算 →
    ├─→ 安全: 无操作
    └─→ 危险: Pub/Sub广播预警
```

**基准负载设计**:
```python
# 文件: experiment/migration/transportation/bench_v2x_communication.py
特点:
- 多车辆模拟: 100-1000辆车并发
- 真实移动模型: 道路约束、速度变化、转向行为
- 地理查询: GEORADIUS查询周边车辆（热点操作）
- 事件驱动: 急刹、碰撞预警触发Pub/Sub
```

#### **场景5: 智能信号灯控制 (Adaptive Traffic Signal)**

**业界应用实例**:
- **Miovision**: 交通信号优化平台
- **阿里云城市大脑**: 信号灯AI调度
- **IBM Intelligent Traffic**: 自适应信号控制

**内存优先原因**:
- 实时流量统计（路口等待车辆数）
- 信号灯状态需快速读写（<50ms）
- 多路口协同需要状态同步

**容器化方案**:
```yaml
容器类型: Redis + InfluxDB
- Redis Hashes: 路口实时状态（绿灯时长、等待队列）
- Redis Sorted Sets: 优先级队列（紧急车辆优先）
- Redis Pub/Sub: 路口间状态同步
- InfluxDB: 流量历史数据（训练优化模型）
```

### 2.4 视频分析 (Video Analytics)

#### **场景6: 智能监控与事件检测 (Surveillance Analytics)**

**业界应用实例**:
- **海康威视 AI Cloud**: 边缘智能监控
- **大华DeepHub**: 视频结构化与分析
- **商汤 SenseFoundry**: 边缘视频分析平台

**内存优先原因**:
- 视频帧推理结果临时缓存（避免重复推理）
- 目标追踪需要短期历史（最近N帧）
- 事件检测需要时间窗口内的多帧关联

**容器化方案**:
```yaml
容器类型: Redis + MongoDB
- Redis Hashes: 目标追踪状态（人/车ID → 最后位置）
- Redis Lists: 帧级检测结果（FIFO队列，保留最近100帧）
- Redis Bitmaps: 人流量热力图（空间占用统计）
- MongoDB: 重要事件持久化（人脸识别、异常行为）

数据流:
视频流 → 目标检测 →
  目标追踪 (Redis Hashes) →
  行为分析 (查询最近N帧) →
    ├─→ 正常: 更新追踪状态
    └─→ 异常: 保存到MongoDB + 告警
```

**基准负载设计**:
```python
# 文件: experiment/migration/video/bench_surveillance_analytics.py
特点:
- 多摄像头并发: 16-64路视频流
- 帧率模拟: 10-30 FPS，每帧产生检测结果
- 目标追踪: 跨帧关联（读取历史状态）
- 缓存策略: LRU淘汰（目标消失后清理）
- 热点数据: 出入口摄像头数据量>>内部
```

## 三、容器选择矩阵 (适用于边缘runc容器)

### 3.1 推荐容器及适用场景

| 容器名称 | 主要用途 | 内存优先场景 | 持久化能力 | 边缘适配性 |
|---------|---------|-------------|-----------|----------|
| **Redis** | 通用缓存、队列、Pub/Sub | ⭐⭐⭐⭐⭐ | RDB/AOF | ⭐⭐⭐⭐⭐ |
| **InfluxDB** | 时序数据库 | ⭐⭐⭐⭐ | TSM引擎 | ⭐⭐⭐⭐ |
| **TimescaleDB** | 时序数据（SQL兼容） | ⭐⭐⭐ | PostgreSQL | ⭐⭐⭐ |
| **MongoDB** | 文档数据库 | ⭐⭐⭐ | WiredTiger | ⭐⭐⭐⭐ |
| **Elasticsearch** | 搜索引擎、日志分析 | ⭐⭐⭐ | Lucene | ⭐⭐⭐ |
| **KeyDB** | Redis分支（多线程） | ⭐⭐⭐⭐⭐ | 同Redis | ⭐⭐⭐⭐⭐ |
| **DragonflyDB** | 现代Redis替代 | ⭐⭐⭐⭐⭐ | 同Redis | ⭐⭐⭐⭐ |
| **Memcached** | 纯内存缓存 | ⭐⭐⭐⭐⭐ | 无 | ⭐⭐⭐⭐⭐ |
| **etcd** | 分布式KV（强一致） | ⭐⭐⭐⭐ | Raft日志 | ⭐⭐⭐⭐ |
| **Apache Kafka** | 消息队列（高吞吐） | ⭐⭐⭐ | 磁盘日志 | ⭐⭐⭐ |
| **NATS** | 轻量消息系统 | ⭐⭐⭐⭐ | JetStream | ⭐⭐⭐⭐⭐ |
| **Valkey** | Redis 7.2分支（开源） | ⭐⭐⭐⭐⭐ | 同Redis | ⭐⭐⭐⭐⭐ |

### 3.2 容器镜像资源消耗

| 容器 | 最小内存 | 镜像大小 | 启动时间 | 边缘友好度 |
|-----|---------|---------|---------|----------|
| Redis | 16MB | ~30MB | <1s | 极佳 |
| KeyDB | 32MB | ~40MB | <1s | 极佳 |
| Memcached | 8MB | ~8MB | <1s | 极佳 |
| InfluxDB | 256MB | ~300MB | 2-3s | 良好 |
| MongoDB | 512MB | ~400MB | 3-5s | 中等 |
| Elasticsearch | 1GB | ~800MB | 10-20s | 较差 |
| NATS | 16MB | ~15MB | <1s | 极佳 |
| etcd | 64MB | ~50MB | <2s | 极佳 |

# 真实边缘场景负载基准测试

## 概述

本目录包含基于真实边缘计算场景设计的负载基准测试套件，用于评估容器迁移性能。这些负载代表了实际边缘应用的内存访问模式、数据流特征和性能要求。

## 为什么需要真实边缘负载？

### 现有负载的局限性
- **过于合成**: 简单的随机数据生成，不反映真实应用行为
- **缺乏边缘特性**: 没有体现边缘计算的资源约束、延迟敏感性
- **应用场景模糊**: 难以与实际工业应用建立联系

### 真实负载的价值
1. **研究可信度**: 使用真实场景提高研究成果的可信度和可复现性
2. **性能评估准确性**: 真实的数据分布和访问模式更准确反映实际性能
3. **应用指导意义**: 研究结果可直接指导实际边缘应用部署

---

## 为什么边缘应用需要热迁移？

### 容器热迁移的必要性

边缘计算场景中，**有状态容器的热迁移（Live Migration）**不是可选功能，而是**业务连续性的关键保障**。

#### 核心挑战：状态 + 延迟 + 移动性

```
传统云计算：
- 服务器固定、资源充足
- 用户距离远、延迟容忍度高
- 状态可持久化到云端

边缘计算：
- 设备移动、资源受限
- 用户近距离、延迟要求严格
- 状态在内存中、丢失即中断
```

**问题**: 如何在设备/服务需要移动时，保持服务不中断？

**答案**: 热迁移 - 在保持服务运行状态下，将容器从一个节点迁移到另一个节点。

---

### 热迁移 vs 冷迁移：为什么冷迁移不够？

| 维度 | 冷迁移 (Stop-and-Copy) | 热迁移 (Live Migration) | 差异影响 |
|-----|---------------------|----------------------|---------|
| **服务中断** | 完全停止（秒-分钟级） | 最小中断（毫秒-秒级） | **关键业务不可接受长中断** |
| **内存状态** | 丢失或需完整转储 | 增量同步（dirty pages） | **状态恢复成本高** |
| **用户体验** | 连接断开、重新建立 | 透明切换 | **实时应用无法容忍** |
| **数据一致性** | 可能丢失未持久化数据 | 保证状态一致性 | **关键任务场景要求** |

#### 实际影响案例

**工业IoT监控（冷迁移）**:
- ❌ 停机5秒 → 丢失500个数据点（100Hz采样）
- ❌ 重启后缓存清空 → 需要重新建立基线（1-2分钟）
- ❌ 异常检测算法失效 → 可能错过故障预警

**工业IoT监控（热迁移）**:
- ✅ 中断<50ms → 丢失<5个数据点（可容忍）
- ✅ 内存状态保留 → 滑动窗口、统计量不丢失
- ✅ 异常检测持续 → 业务无感知

**视频监控（冷迁移）**:
- ❌ 停机10秒 → 丢失150帧（15 FPS）
- ❌ 追踪状态丢失 → 需要重新识别所有目标
- ❌ 可能错过关键事件（入侵、事故）

**视频监控（热迁移）**:
- ✅ 中断<100ms → 丢失<2帧（可容忍）
- ✅ 追踪ID保留 → 目标轨迹连续
- ✅ 事件检测不间断

**V2X通信（冷迁移）**:
- ❌ 停机1秒 → 车辆位置过期（60km/h = 16.7m位移）
- ❌ 邻近车辆缓存清空 → 碰撞预警失效
- ❌ **安全关键场景 - 不可接受**

**V2X通信（热迁移）**:
- ✅ 中断<10ms → 位置偏差<0.17m（可容忍）
- ✅ 位置索引保留 → 邻近查询持续
- ✅ 安全预警不中断

---

### 边缘容器迁移的真实触发场景

#### 场景1: 边缘节点故障/维护 🔧

**触发条件**:
- 硬件故障（服务器过热、磁盘损坏）
- 计划维护（系统升级、安全补丁）
- 资源耗尽（内存/CPU过载）

**实际案例**:
- **智能工厂**: 边缘服务器需要升级，但产线不能停（24x7运行）
  - 冷迁移：停产5分钟，损失数万元
  - 热迁移：透明切换，零损失

- **智慧医院**: 病房监护边缘节点硬件故障
  - 冷迁移：患者监控中断，可能危及生命
  - 热迁移：监护持续，患者安全

**迁移频率**: 每月1-2次（计划维护）+ 不定期（故障）

---

#### 场景2: 用户/设备移动 🚗

**触发条件**:
- 车辆移出覆盖范围（V2X）
- 用户跨区域移动（AR/VR应用）
- 移动机器人换区（AGV、无人机）

**实际案例**:
- **自动驾驶**: 车辆从路口A驶向路口B，MEC服务需跟随
  - 路口A边缘节点 → 路口B边缘节点
  - 要求：<10ms切换（安全关键）
  - 状态：车辆轨迹、周边车辆缓存、V2I通信状态

- **移动AR**: 游客在景区移动，AR服务跟随切换
  - 景点A边缘 → 景点B边缘
  - 要求：<100ms切换（用户体验）
  - 状态：渲染缓存、定位数据、交互历史

- **仓储AGV**: 机器人跨区域作业
  - 仓库A边缘 → 仓库B边缘
  - 要求：<50ms切换（避免碰撞）
  - 状态：路径规划、任务队列、协同状态

**迁移频率**: 高频（每小时数次-数十次）

---

#### 场景3: 负载均衡/资源优化 ⚖️

**触发条件**:
- 边缘节点负载不均（热点区域过载）
- 能耗优化（迁移到低功耗节点）
- 网络优化（靠近数据源）

**实际案例**:
- **智慧园区**: 早高峰时出入口监控负载激增
  - 将部分视频分析容器迁移到轻载节点
  - 要求：迁移时不中断监控
  - 状态：目标追踪缓存、帧缓冲、检测模型缓存

- **零售门店**: 促销时段客流量激增
  - 动态迁移推荐引擎到更强算力节点
  - 要求：用户会话不丢失
  - 状态：购物车、浏览历史、推荐缓存

**迁移频率**: 中频（每天数次，随负载波动）

---

#### 场景4: 网络拓扑变化 🌐

**触发条件**:
- 网络链路故障/拥塞
- 5G切换（宏基站 ↔ 微基站）
- 运营商切换（多链路场景）

**实际案例**:
- **车联网**: 5G宏基站故障，切换到备用基站
  - V2X服务容器需迁移到新基站MEC
  - 要求：<10ms切换（安全关键）
  - 状态：车辆位置索引、交通事件队列

- **远程医疗**: 主链路拥塞，切换到备用链路
  - 患者监护容器迁移到备用边缘节点
  - 要求：不丢失生命体征数据
  - 状态：实时数据流、异常检测模型状态

**迁移频率**: 低频但关键（每周数次）

### 内存状态优先的必然性

#### 为什么不能简单持久化到磁盘？

| 方案 | 延迟 | 吞吐量 | 状态恢复时间 | 适用场景 |
|-----|------|--------|------------|---------|
| **纯内存** | <1ms | 100K+ ops/s | <50ms（热迁移） | **实时边缘应用** |
| **内存+RDB持久化** | ~10ms | ~10K ops/s | 1-5秒（加载RDB） | 非关键应用 |
| **内存+AOF持久化** | ~100ms | ~1K ops/s | 5-30秒（重放日志） | 对一致性要求高 |
| **纯磁盘数据库** | ~10ms | ~1K ops/s | 10-60秒（数据库启动） | 云端应用 |

**边缘应用的困境**:
- ❌ 磁盘持久化太慢 → 延迟不满足要求（<10ms）
- ❌ 完整持久化太大 → 迁移时间长（数GB内存）
- ❌ 冷启动太慢 → 服务中断不可接受（数十秒）

**热迁移的优势**:
- ✅ 内存增量同步 → 仅传输dirty pages（通常<10%）
- ✅ 服务持续运行 → 用户无感知
- ✅ 状态完整保留 → 缓存、统计量不丢失

```
冷迁移（Stop-and-Copy）:
  停止服务：          1s
  完整内存转储：      8-10s  (1GB / 100MB/s)
  传输到目标节点：    10-12s (1GB / 100MB/s)

  ────────────────────────────
  总中断时间：        21-26s  ❌ 不可接受

热迁移（Live Migration with Dirty Tracking）:
  预拷贝阶段（服务运行）：  5-8s   (传输大部分内存)
  增量同步（2-3轮）：       2-3s   (仅传输dirty pages)
  最后切换：                0.05-0.1s
  ────────────────────────────
  服务中断时间：      <100ms  ✅ 可接受
  总迁移时间：        7-11s   (但服务不中断)
```

### 本基准测试的验证目标

通过这些真实边缘负载，我们可以验证：

#### 1. 内存访问模式
- **写密集程度**: 不同应用的dirty page产生速率
- **访问局部性**: 热点数据分布（影响迁移策略）
- **状态大小**: 实际工作集大小（影响迁移时间）

#### 2. 迁移性能影响
- **业务中断时间**: 最后切换阶段的服务不可用时长
- **性能下降**: 迁移过程中的QPS/延迟波动
- **数据一致性**: 迁移前后状态是否完整

#### 3. Dirty Tracking优化
- **追踪开销**: dirty page追踪机制的CPU/内存开销
- **增量同步效率**: 多轮迭代的收敛速度
- **优化策略**: 不同负载的最佳迁移策略

#### 4. 实际可行性
- **迁移成功率**: 不同负载的迁移成功率
- **资源消耗**: 迁移过程的网络/CPU/内存消耗
- **可用性保障**: SLA目标达成情况（如99.9%可用性）

- **冷迁移影响**: 停机1秒 → 位置过期16.7m → 邻近车辆缓存清空 → 碰撞预警失效 → **安全风险**
- **热迁移收益**: 中断<10ms → 位置偏差<0.17m → 位置索引保留 → 安全预警持续
- **业务价值**: 保障行车安全，满足V2X安全关键要求（ISO 26262）
- **迁移频率**: 高频（城市道路每辆车每小时可能触发5-20次切换）

**超低延迟要求（<10ms）

**内存优先理由**:
- 超低延迟要求（<10ms响应）
- 高频位置更新（每辆车10-100 Hz）

## 迁移实验中的使用

### 验证热迁移的价值

这些负载设计用于验证**边缘有状态服务热迁移的必要性和可行性**：

#### 实验设计思路

```
1. 建立基线（无迁移）
   ├─ 运行负载，记录正常QPS、延迟、内存使用
   └─ 统计dirty page产生速率

2. 冷迁移对比（Stop-and-Copy）
   ├─ 停止容器 → 完整内存转储 → 传输 → 恢复
   ├─ 测量：服务中断时间、状态丢失情况
   └─ 记录：用户体验影响（丢失数据量、恢复时间）

3. 热迁移验证（Live Migration）
   ├─ 预拷贝 → 增量同步 → 最后切换
   ├─ 测量：服务中断时间、dirty page追踪开销
   └─ 记录：业务影响（QPS下降、延迟抖动）

4. 对比分析
   ├─ 中断时间：冷迁移 vs 热迁移（数量级差异）
   ├─ 状态保留：冷迁移状态丢失 vs 热迁移状态保留
   └─ 业务影响：服务质量下降程度
```

### 测试 Dirty Page 追踪

### 预期结果

不同负载的迁移特征差异：

- **工业IoT（预测性维护）**:
  - Dirty pages: 大量连续（Stream写入）
  - 产生速率: 极高（10-100 MB/s）
  - 迁移挑战: 需多轮迭代才能收敛
  - 中断容忍度: <100ms
  - **验证点**: 高频写入场景下dirty tracking的性能开销

- **视频监控（智能分析）**:
  - Dirty pages: 离散分散（Hash更新、List操作）
  - 产生速率: 中等（5-20 MB/s）
  - 迁移挑战: 页面分散，需要高效的追踪机制
  - 中断容忍度: <500ms
  - **验证点**: 离散写入模式下迁移策略优化

- **V2X通信（车联网）**:
  - Dirty pages: 极高频率（Geo索引更新）
  - 产生速率: 极高（50-200 MB/s）
  - 迁移挑战: 写入速度快，难以收敛
  - 中断容忍度: <10ms（安全关键）
  - **验证点**: 超低延迟要求下的迁移可行性

### 关键性能指标（KPI）

| 指标 | 冷迁移目标 | 热迁移目标 | 测量方法 |
|-----|----------|----------|---------|
| **服务中断时间** | 5-30秒 | <100ms | 测量容器停止→恢复时间 |
| **数据丢失量** | 显著（缓存清空） | 最小（仅最后未同步） | 对比迁移前后状态 |
| **QPS下降** | 100%（完全停止） | <20%（迁移期间） | 监控客户端请求成功率 |
| **延迟抖动** | N/A（服务停止） | P99 < 2x正常值 | 统计延迟分布变化 |
| **状态一致性** | 需重建（秒-分钟） | 完整保留（毫秒） | 验证缓存、统计量 |
| **迁移总时间** | 10-60秒 | 5-15秒 | 从触发到完成的总时间 |
| **网络流量** | 全量（GB） | 增量（100-500MB） | 监控网络传输量 |

## 常见问题

### Q1: 为什么不直接使用 YCSB/redis-benchmark？

A: 通用基准测试无法体现边缘计算的特殊性：
- 边缘有严格的延迟要求（<10ms）
- 数据有时间/空间局部性
- 应用有特定的读写模式
- 资源约束更严格（内存/带宽）

### Q2: 如何选择适合我研究的场景？

A: 根据研究重点选择：
- **高频写入**: 工业IoT（测试 dirty page 追踪）
- **读写混合**: 视频监控（测试缓存策略）
- **超低延迟**: V2X通信（测试迁移中断影响）

### Q3: 可以在实际生产环境使用吗？

A: 这些是基准测试，**不建议**直接用于生产：
- 缺少错误恢复机制
- 没有完整的数据持久化
- 未经过安全审计

但可以作为原型参考实现生产系统。
